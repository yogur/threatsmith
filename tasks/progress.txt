## Codebase Patterns
- Build step invocation: `uv run python scripts/build_skills.py` — regenerates `build/skills/` from `skills-src/`. Run this whenever a skill source or canonical reference changes. The committed `build/skills/` is the installable artifact; never hand-edit it.
- `SKILL_SHARED_REFS` in `src/threatsmith/_build_skills.py` is the authoritative map of which shared references each skill bundles. When a new shared reference is added to `_shared/references/` and a skill needs it, add the filename to that skill's list and rebuild.
- New skills-src/ tree: authored skill sources live in `skills-src/` at repo root; shared reference markdown is in `skills-src/_shared/references/`. Never edit files under `build/skills/` directly — those are generated by the build step.
- Reference content source of truth: `skills-src/_shared/references/` holds the canonical markdown files. The Python constants in `src/threatsmith/frameworks/references/` remain for now (they back the current assembler) but will be retired as US-007/US-008/US-009 land.
- Assembler is now `compose_stage_instruction()` (not `assemble_prompt()`). It returns a per-stage instruction string — skill name, stage number+name, mode, output dir, file-pointer prior-output hint, non-interactive signal. No prior-stage text inlined. US-008/US-009 will complete the removal of Python prompt constants.
- `FrameworkPack.skill_name` is the installed skill identifier. Both built-in packs set it (threatsmith-stride-4q, threatsmith-pasta). Any new framework pack must set `skill_name` for Model B orchestration to work.
- `detect_scanners()` and `utils/scanners.py` are removed. Scanner detection is fully delegated to the agent via `skills-src/_shared/references/scanners.md`. No CLI-side scanner detection remains.
- `Engine.__init__` and `get_engine()` no longer accept `scanner_names`. Engine permission management for Bash/scanner tools is not wired at the CLI level after this refactor — address in a future story if needed.
- `ThreatSmithMetadata` no longer has `scanners_available`/`scanners_unavailable` fields. `generate_metadata()` no longer accepts scanner args. metadata.json is leaner as a result.
- Framework skill sources: a skill lives at `skills-src/<skill-name>/` with `SKILL.md` + `references/stages/NN-*.md`. Authored sources do NOT include the shared reference files — stage files cite them by skill-root-relative path (`references/owasp-api-top-10.md`), and the build step (US-006) syncs the matching `_shared/references/*.md` into each skill's `references/`. Keep stage deliverable filenames identical to the framework pack's `output_file` values (01-system-model.md … 05-report.md), since the CLI/report stage rely on them.
- Skill stages read prior outputs by path (e.g. "read `01-system-model.md` from the output directory") — never inline prior-stage text. Default output dir is `threatmodel/`.
- Skill sources must be execution-context-agnostic: a coding agent may run a skill standalone on a user's machine, so do NOT mention the ThreatSmith CLI, "this prompt", prompt injection, "pasted/inlined" prior content, or whether a run is interactive vs. orchestrated. State the behavior plainly ("read X from the output directory"), not the harness mechanics. (US-002 review)
- Mode framing maps to SDLC phases, not just input source: `from-code` = after implementation (analyze code + any docs; code is the primary source of truth, docs corroborate; also fits design-phase work where code is paired with fresh docs for an unbuilt feature); `from-docs` = during design/requirements (not yet implemented); `pair` = interactive during design/early development. Apply the same framing to the PASTA skill (US-003).
- No hard-coding of details that a shared reference already owns. `scanners.md` is the single source of truth for which scanner tools exist and how to run them — stage files must point at it ("detect which scanners are available and run the ones present"), never list tool names like Semgrep/Trivy/Gitleaks inline. Same principle for any future shared reference: name the file, not its contents. (US-002 review)
- STRIDE categories live inline in the threat-identification stage file, NOT in a shared reference. In stride-4q that's stage 02 ("Systematic STRIDE analysis"); in PASTA it's stage 04, pillar 1 ("STRIDE threat analysis"). There is intentionally no `skills-src/_shared/references/stride-categories.md`.
- "Note the system's nature for downstream reference selection" (records whether the system exposes APIs / integrates an LLM / has a mobile client, so the threat stage's conditional OWASP selection is accurate) goes in the stage that catalogs the attack surface: stride-4q stage 01 (system model), PASTA stage 03 (decomposition). The conditional OWASP guidance itself lives in the threat stage (stride-4q stage 02, PASTA stage 04).
- Interactivity is orthogonal to single-stage: a person may run one stage interactively, while the orchestrator drives stages non-interactively. SKILL.md conditions the behavior on the invocation ("when the invocation is non-interactive … run to completion without pausing; proceed with the best-supported interpretation and record assumptions instead of asking"), rather than declaring an entry point inherently non-interactive. The orchestrator (US-007) is expected to signal non-interactive in the per-stage instruction it passes to the engine. (US-004)
- Consumption skills (threatsmith-secure) are a single self-contained SKILL.md with no references/ dir and no synced shared references (PRD §2.1) — unlike the framework skills. They are source-agnostic: bind only to "readable threat-model markdown in a directory", extract the substance (threats / boundaries / required mitigations / accepted risk) rather than parsing specific filenames, section headings, or a fixed stage layout, so hand-authored models work. metadata.json is optional and used only opportunistically (staleness hint), never required. The build step (US-006) syncs nothing into this skill — it has no shared refs. (US-005)

  - `references/__init__.py` is now an empty shell. It can be deleted in a future cleanup pass if nothing imports from the `references` package directly — for now, keeping it avoids breaking any external code that does `from threatsmith.frameworks.references import ...`.
  - After US-009, `FrameworkPack` has exactly 6 fields: `name`, `display_name`, `description`, `stages`, `report_stage`, `skill_name`. Any new framework pack needs only those.
