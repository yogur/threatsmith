## Codebase Patterns
- New skills-src/ tree: authored skill sources live in `skills-src/` at repo root; shared reference markdown is in `skills-src/_shared/references/`. Never edit files under `build/skills/` directly — those are generated by the build step.
- Reference content source of truth: `skills-src/_shared/references/` holds the canonical markdown files. The Python constants in `src/threatsmith/frameworks/references/` remain for now (they back the current assembler) but will be retired as US-007/US-008/US-009 land.
- Framework skill sources: a skill lives at `skills-src/<skill-name>/` with `SKILL.md` + `references/stages/NN-*.md`. Authored sources do NOT include the shared reference files — stage files cite them by skill-root-relative path (`references/owasp-api-top-10.md`), and the build step (US-006) syncs the matching `_shared/references/*.md` into each skill's `references/`. Keep stage deliverable filenames identical to the framework pack's `output_file` values (01-system-model.md … 05-report.md), since the CLI/report stage rely on them.
- Skill stages read prior outputs by path (e.g. "read `01-system-model.md` from the output directory") — never inline prior-stage text. Default output dir is `threatmodel/`.
- Skill sources must be execution-context-agnostic: a coding agent may run a skill standalone on a user's machine, so do NOT mention the ThreatSmith CLI, "this prompt", prompt injection, "pasted/inlined" prior content, or whether a run is interactive vs. orchestrated. State the behavior plainly ("read X from the output directory"), not the harness mechanics. (US-002 review)
- Mode framing maps to SDLC phases, not just input source: `from-code` = after implementation (analyze code + any docs; code is the primary source of truth, docs corroborate; also fits design-phase work where code is paired with fresh docs for an unbuilt feature); `from-docs` = during design/requirements (not yet implemented); `pair` = interactive during design/early development. Apply the same framing to the PASTA skill (US-003).
- No hard-coding of details that a shared reference already owns. `scanners.md` is the single source of truth for which scanner tools exist and how to run them — stage files must point at it ("detect which scanners are available and run the ones present"), never list tool names like Semgrep/Trivy/Gitleaks inline. Same principle for any future shared reference: name the file, not its contents. (US-002 review)
- STRIDE categories live inline in the stride-4q stage 02 file (the "Systematic STRIDE analysis" section), NOT in a shared reference. There is intentionally no `skills-src/_shared/references/stride-categories.md`.
